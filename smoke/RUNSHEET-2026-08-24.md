## SMOKE 4 — Painter PH2, the six multi-paint kinds

**Judge this one in `jas_dioxus`** — PH2 is the Rust painter conversion
(`jas_dioxus/src/painter/element_render.rs`).

    cd jas_dioxus && dx serve
    # then open smoke/03-painter-ph2.svg

The scene holds one **convertible** instance of each of the six kinds PH2
converted — Rect · Circle · Ellipse · Polygon · Polyline · Path — each with a
plain solid fill and a plain solid centre-aligned stroke, so **every one is drawn
by the NEW path.** That arm has never been looked at.

**PASS:** all six render as they did before the painter conversion —

| look at | PASS |
|---|---|
| fill and stroke together | fill under stroke, no doubled edge, no gap between them |
| stroke placement | centred on the outline, not inside or outside it |
| where fill meets stroke | no alpha shift or dark seam — the two paints compose as one |
| the open polyline (5) | stroked only, no phantom fill closing it |
| the closed path (6) | closes cleanly at the `Z` |

**Worth knowing while you look:** PH2 routes to the new seam **only** when the
paint is display-list-equivalent to the legacy body; anything it cannot reproduce
exactly (set stroke brush, variable width, arrowheads, anchor-aligned dashing
that expands into sub-paths, inside/outside on an ellipse arc, freeform
gradients) **falls back to the legacy arm**. The scene deliberately contains none
of those, so what you are judging is the converted path alone. If you want the
fallback arm too, drawing any shape with a gradient exercises it.

*One codec note, so it does not surprise you: opening and re-saving this scene
tightens the document `viewBox` from `0 0 600 400` to the content bounds
(`36 33 513 291`). That is the codec's standing behaviour, not something tonight
introduced — all six shapes survive intact either way.*

## D-α (#14) LANDED TODAY — and it is NOT judgeable tonight. Do not go hunting.

The masked-element opacity repair (`MASKALPHA`, `c59e5349`) merged this morning,
after this sheet was first written. Its own commit message says it is pinned by
no golden and that no smoke scene carries a mask. **Checked at HEAD, it is
stronger than that: no masked element can be produced in the running app at
all**, on four independent paths —

- `open_file` is **filtered to SVG** (`workspace/actions.yaml:79`), and the SVG
  codec has exactly **one** occurrence of `mask` in the whole file —
  `mask: None` at `geometry/svg.rs:1624`. Masks are neither parsed nor written,
  so no `.svg` can carry one in.
- **`MAKE_MASK` / `MASK_PREVIEW` appear nowhere in `workspace/*.yaml`.** The only
  `mask` words there are CROP_BUTTON's prose (a different feature — crop, mask
  consumed) and two icon comments. By this house's own doctrine that jas-specific
  features are defined through the workspace YAML, there is no menu item, button
  or shortcut that makes one.
- `make_mask_on_selection` (`document/controller.rs:1403`) would create a mask
  with an **empty** subtree, and populating it needs mask-editing mode, which its
  own docstring defers to **Phase 4**.
- PH4 does not exist: `painter/canvas2d.rs:238,242` are
  `unimplemented!("mask layers are PH4; masked elements must stay on the legacy path")`.

So the repair is real, tested and correct — three discriminating unit tests, and
it moved Rust **into** agreement with Swift — but there is nothing on the canvas
for an eye to judge, and an hour spent looking for a mask to open would find
none. **The eyeball D-α is owed comes with PH4, not tonight.**
